作成 2026-07-25。コード変更（フェーズ0〜5）は完了済み。
本書は **Claude が実行できないコンソール操作**（DNS・LINE Console・シークレット）の手順書。

> ⚠️ **順番が重要。** 下の「実施順」を守らないと、既存ユーザーのログインが一時的に壊れる。
> 理由は §0 を読むこと。

## 0. なぜ順番が重要か（先に読む）

新しいビルドのページは、リンクを **ルート相対**（`/login/` `/account/` `/map/`）で持つ。
これは `tsudumon.jp` の直下に置かれる前提の書き方。

一方、現在の本番は `www.chatstudy.jp/tsudumon/` で配信されている。
ここに新ビルドをデプロイすると、ページ内の `/login/` は
`www.chatstudy.jp/login/` を指してしまい **存在しない**（chatstudy の SPA に吸われる）。

```
新ビルドを chatstudy.jp 経由で配信した場合:
  ページ: https://www.chatstudy.jp/tsudumon/ref/05/
  リンク: /login/  →  https://www.chatstudy.jp/login/   ← 壊れる
```

したがって「**新ドメインが使える状態にしてからデプロイし、間を空けずに
chatstudy.jp を301へ切り替える**」必要がある。

### 実施順（この通りに）

| # | 作業 | 場所 | 所要 | 影響 |
|---|---|---|---|---|
| 1 | LINE コールバックURL追加 | LINE Developers | 5分 | なし（追加のみ） |
| 2 | `GEMINI_API_KEY` を Functions へ | ローカル（`functions/.env`） | 5分 | なし |
| 3 | カスタムドメイン登録 + DNS | Firebase + お名前.com | 15分＋反映待ち | なし |
| 4 | SSL 発行完了を待つ | — | 数十分〜最大24h | なし |
| 5 | **デプロイ**（Claudeが実行・要承認） | — | 5分 | ここから切替 |
| 6 | **Vercel を301へ**（Claudeが実行・要承認） | — | 5分 | 旧URL救済 |

1〜4 は**いつやっても既存サービスに影響しない**ので、先に全部済ませてよい。
5と6は**続けて実施**する（間が空くほど、旧URLで壊れたリンクを踏む人が出る）。

## 1. LINE Developers Console — コールバックURLの追加

### 前提知識

LINE のチャネルは種類が違うものが複数ある。**触るのは「LINEログインチャネル」だけ**。

| チャネル | ID | 役割 | 今回触るか |
|---|---|---|---|
| **LINEログイン** | `2009587166` | Webページからの LINE ログイン（OAuth）。LIFF もここにぶら下がる | **✅ ここだけ** |
| Messaging API（一問一答） | （既存） | チャットでスタディ `@824cebif` の Bot | ❌ 触らない |
| Messaging API（つづもん） | `2010838149` | つづもん `@215uijik` の Bot | ❌ 触らない |

> ⚠️ ログインチャネル `2009587166` は **chatstudy の LIFF（settings / report / units 等）と共用**。
> 既存のコールバックURLは**消さず、追加だけ**すること。

### 手順

1. https://developers.line.biz/console/ を開く
2. つづもん／チャットでスタディのプロバイダーを選ぶ
3. チャネル一覧から **「LINEログイン」種別のチャネル（ID `2009587166`）** を開く
4. 上部タブ「**LINEログイン設定**」を開く
5. 「**コールバックURL**」の欄を編集する
6. 既存の行はそのままに、**改行して次の2行を追加**する

```
https://tsudumon.jp/login/
https://tsudumon.jp/activate/
```

7. 「更新」を押す

### 注意

- **末尾のスラッシュまで完全一致**が必要。`https://tsudumon.jp/login`（スラッシュ無し）では動かない。
  コード側は `location.origin + '/login/'` を送るため、必ず `/login/` と `/activate/`。
- 旧URL2本（`https://www.chatstudy.jp/tsudumon/login/` と `.../activate/`）は
  **当面残す**。301の猶予期間中に旧URLへ戻ってくる人の保険になる。
- なぜ2本要るか: `login/index.html` と `activate/index.html` が
  それぞれ自分自身を `redirect_uri` にして OAuth を完結させる設計のため。

## 2. GEMINI_API_KEY を Cloud Functions に設定

LPのAIチャットが Vercel 関数から Cloud Function へ移ったので、
APIキーの置き場も Vercel から Firebase Functions へ移す。

### 2-1. 今の値を Vercel から取り出す

1. https://vercel.com/ にログイン
2. chatstudy.jp のプロジェクト → **Settings** → **Environment Variables**
3. `GEMINI_API_KEY` の値を表示（目のアイコン）してコピー
   - `CHAT_DAILY_LIMIT` / `CHAT_USER_DAILY_LIMIT` を設定している場合はそれも控える

> 別の入手先: Google AI Studio（https://aistudio.google.com/apikey）で新しいキーを発行してもよい。

### 2-2. functions/.env に書く

`marutto-study/functions/.env` をエディタで開き、末尾に追記:

```
GEMINI_API_KEY=<コピーした値>
```

`CHAT_DAILY_LIMIT` / `CHAT_USER_DAILY_LIMIT` は**省略可**
（未設定なら 300 / 15 が既定値として使われる）。変えたいときだけ書く:

```
CHAT_DAILY_LIMIT=300
CHAT_USER_DAILY_LIMIT=15
```

### 注意

- `functions/.env` は gitignore 済み。**この値を Claude に見せる／貼り付ける必要はない**。
- すでに `GEMINI_API_KEY` が書かれている可能性が高い
  （公式LINEのAIチャット `aiChat.ts` が同じキー名を使っている）。
  **その場合は何もしなくてよい。** 重複して書かないこと。
  → 確認方法: ファイル内に `GEMINI_API_KEY` の行が既にあるか見るだけ。
- キーが未設定でもデプロイは通り、チャットは
  「ただいまチャットを準備中です…公式LINEでご質問ください」という
  フォールバック文を返す（＝致命的ではないが、LPのチャットが機能しない）。

## 3. カスタムドメイン登録（Firebase）と DNS 設定（お名前.com）

### 3-1. Firebase 側でドメインを追加して、必要なレコードを表示させる

1. https://console.firebase.google.com/ を開く
2. プロジェクト **chatstudy-63477** を選ぶ
3. 左メニュー **構築 → Hosting**
4. サイトの一覧から **`tsudumon`**（`tsudumon.web.app`）を選ぶ
   - ⚠️ `chatstudy-63477`（デフォルトサイト）や `mubista` と間違えないこと
5. 「**カスタムドメインを追加**」をクリック
6. ドメイン名に `tsudumon.jp` と入力
7. 「**既存のウェブサイトにリダイレクトする**」のチェックは **入れない**（重要）
   - これは「このドメインを、別URLへ転送するだけの存在にする」オプション。
     旧ドメイン→新ドメインの引っ越しに使う機能で、**今回の用途とは逆**。
   - チェックなし ＝ `tsudumon.jp` が Hosting サイト `tsudumon` の中身を配信する（これが正解）
   - チェックあり ＝ `tsudumon.jp` が中身を持たず、どこかへ転送するだけになる
8. 「続行」を押すと、**所有権確認用の TXT レコード**が表示される
   → この画面は開いたままにする（3-2 で使う）

### 3-2. お名前.com に TXT レコードを登録

1. https://www.onamae.com/ → 「ドメインNavi」にログイン
2. 上部メニュー **ドメイン** → **ドメイン機能一覧**
3. 「ネームサーバーの設定」の中の **DNS関連機能の設定** をクリック
4. `tsudumon.jp` にチェック → **次へ**
5. 「**DNSレコード設定を利用する**」の **設定する** をクリック
6. 入力欄に、Firebase が表示した TXT レコードを入れる:

   | 項目 | 入力値 |
   |---|---|
   | ホスト名 | **空欄**（＝ドメイン自体。`@` とは書かない） |
   | TYPE | `TXT` |
   | TTL | `3600`（既定のまま） |
   | VALUE | Firebase が表示した文字列をそのまま貼る |

7. 「**追加**」ボタンを押す（→ 下の一覧に行が増える）
8. ページ下部の「**確認画面へ進む**」→「**設定する**」

> ⚠️ お名前.com の落とし穴: 「追加」を押しただけでは保存されない。
> 必ず最後に「確認画面へ進む」→「設定する」まで進むこと。

### 3-3. ネームサーバーの確認（⚠️ 2026-07-25 に実際にハマった箇所）

DNSレコード設定が効くのは、そのドメインが**お名前.comのネームサーバー（`01〜04.dnsv.jp`）を
使っている**場合だけ。

**今回の実例**: 取得直後の `tsudumon.jp` はネームサーバーが
`ns-rs1.gmoserver.jp` / `ns-rs2.gmoserver.jp`（＝**GMOレンタルサーバー側のDNS**）を向いていた。
この状態では「DNSレコード設定」に何を入れても、世界中のDNSは gmoserver.jp を見にいくため
**一切反映されない**（`01.dnsv.jp` に問い合わせると `Query refused` が返る＝ゾーンが存在しない）。
A レコードも GMO のサーバー `157.120.209.30` を指したままだった。

**確認と修正**:
- ドメインNavi → **ネームサーバーの設定** → **ネームサーバーの変更**
- `tsudumon.jp` を選び「**お名前.comのネームサーバーを使う**」を選択して確定
- 反映されると `01.dnsv.jp` 〜 `04.dnsv.jp` になる

**確認コマンド**（`dnsv.jp` が返れば成功。`gmoserver.jp` ならまだ）:
```
nslookup -type=NS tsudumon.jp 8.8.8.8
```

反映は数十分〜最大72時間（今回は当日中に完了）。

### 3-3b. 古いAレコードの削除（⚠️ これも実際にハマった）

ネームサーバーを切り替えると、お名前.com側のゾーンに
**レンタルサーバー用の A レコード `157.120.209.30` が引き継がれて残る**ことがある。

Firebase の A レコードと2つ並んだままだと、**アクセスの約半分がGMOのサーバーに飛ぶ**
（つづもんが表示されたりされなかったりする不安定な状態になる）。

- DNSレコード設定を開き、`157.120.209.30` の A レコードを**削除**する
- Firebase が指定した A レコード（例: `199.36.158.100`）だけを残す
- 削除も「**確認画面へ進む**」→「**設定する**」まで押さないと保存されない
- お名前.comのDNS反映は**最大1時間**かかる

**確認コマンド**（Firebase のIPだけが返れば成功）:
```
nslookup -type=A tsudumon.jp 01.dnsv.jp
```

### 3-4. 所有権確認 → A レコード登録

1. TXT の反映を待つ（数分〜1時間）
2. Firebase の画面に戻って「**確認**」を押す
3. 確認が通ると、今度は **A レコード（IPアドレス2件）** が表示される
4. お名前.com の DNSレコード設定に戻り、**A レコードを2件**追加:

   | 項目 | 入力値 |
   |---|---|
   | ホスト名 | **空欄** |
   | TYPE | `A` |
   | TTL | `3600` |
   | VALUE | Firebase が表示した1つ目のIP |

   もう1件、2つ目のIPで同じものを追加する。

5. 「追加」→「確認画面へ進む」→「設定する」

> ⚠️ **IPアドレスは必ず Firebase の画面に表示された値をそのまま使う。**
> ネットの記事に載っている古いIPを使わないこと（Firebase側で変わることがある）。

### 3-5. www.tsudumon.jp も押さえる場合（任意・後回し可）

`tsudumon.jp` が「接続済み」になったあとに、**もう一度**「カスタムドメインを追加」から
`www.tsudumon.jp` を追加する。**このときだけ**「既存のウェブサイトにリダイレクトする」に
チェックを入れ、転送先を `tsudumon.jp` にする（www → apex の301）。

その後 Firebase が表示するレコードを、お名前.com で
**ホスト名に `www`** を入れて追加する。

必須ではない。`www` 付きで来る人がいなければ設定しなくてよい。

### 3-6. SSL 証明書の発行を待つ

- Firebase Hosting のドメイン一覧で、状態が
  「保留中」→「**接続済み**」に変わればOK
- 通常は数十分。**最大24時間**かかることがある
- この間、`tsudumon.jp` は古いビルド（`/tsudumon/` 前提のリンク）を配信するが、
  まだ誰にも公開していないので問題ない

### 3-7. 確認

状態が「接続済み」になったら、ブラウザで:

```
https://tsudumon.jp/_healthz.txt
```

→ `tsudumon-firebase-proxy-live` と表示されればDNS・SSLとも成功。

## 6. 元に戻したくなったら

- `marutto-study/vercel.json` の301を元の rewrite に戻して git push すれば、
